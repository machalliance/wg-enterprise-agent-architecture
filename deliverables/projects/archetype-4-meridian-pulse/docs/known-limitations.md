# Known limitations — accepted prototype scope

Meridian Pulse is a working-group prototype: it exists to show that a single revenue-optimization agent
can perceive, reason, and reprice ~50 SKUs within policy — with real machine identity, a real policy gate
in the write path, real circuit breakers, and an append-only decision trail — and to find out where that
breaks. It is **not** production software, and this file is the honest list of the places where that
distinction is load-bearing.

The README's [Scope boundaries](../README.md#scope-boundaries) section names the *mocked* pieces (commerce,
market data) and the big out-of-scope ones (multi-agent, dashboard hardening). This file is the deeper
engineering catalogue: the accepted architectural shortcuts and the standards/deployment oddities that a
reader evaluating the prototype — or a contributor about to change it — deserves to see spelled out. Each
item was found deliberately in review and then deliberately left in place. Two reasons to publish the list
rather than quietly carry it: a reader deserves to know which properties are *demonstrated* and which are
*asserted*, and a contributor deserves to know which oddities are *decisions* rather than *bugs*.

Nothing here breaks the demo. Each item is real and would matter beyond one.

## Scope note for contributors

Do not act on anything in this file unless that is the task you were given. These are recorded so nobody
re-discovers them as bugs, re-litigates them mid-task, or "helpfully" refactors them unasked. The
invariants that must survive any such work are listed at the end.

## Architecture

**1. Governance state is in-process memory; only the trail and checkpoints are durable.** The kill switch,
the circuit-breaker windows, and the live oversight status all live in RAM inside the control plane
(`OversightState` in `packages/control-plane/src/state.ts`, `CircuitBreakers` in `breakers.ts` — its
rate/burst/anomaly history is an in-memory ring). The two things that survive a restart are the
append-only decision trail (`packages/policy/decision-trail.jsonl`) and the agent's hash-chained
checkpoint store (`packages/agent/checkpoint.db`). So the *evidence* of what happened is durable; the
*state that decides whether the next action may proceed* is not. Restart the control plane mid-run and the
breaker windows reset to empty and a prior `halt()` is forgotten — the agent is un-paused by a process
bounce. Post-prototype fix: persist oversight status and breaker windows to an append-only journal
rehydrated on boot. Related and equally accepted: the kill switch, the breakers, and the escalation queue
share the control-plane process, so the controls die with the thing they control.

**2. The category write-scope block moved from M1 (gateway) to M3 (policy).** The mandate says the agent
may only reprice its own categories (e.g. `outdoor-tents`), never `premium-footwear`. The natural place
for "this identity may not touch that category" is the gateway's `mcpAuthorization` — but AgentGateway's
CEL authorizes by **tool identity, not tool arguments**, and the category is an argument of `set_price`.
So the block lives one layer in, in the policy server, as `ESCALATE:OUT_OF_SCOPE_CATEGORY`
(`packages/policy/src/tiers.ts`, asserted by `tiers.test.ts` — "the block deferred from M1"): an
out-of-scope category cannot execute autonomously, it goes to a human. The gateway still owns identity and
tool-scope (`commerce:write`); the policy server owns argument-level tier routing. This is written into the
`packages/policy/src/index.ts` header on purpose. The property worth preserving: there is no path from
reasoning to a commerce write that skips the policy server, so moving the check inward did not open a hole
— it relocated it to the only layer that can see the argument.

**3. Machine identity is scoped and verifiable, but has no lifecycle.** The agent mints an RSA-signed,
short-TTL JWT locally (`packages/agent/src/identity.js keygen`/`mint`), publishes a public `jwks.json`, and
the gateway verifies it strictly on every MCP call — that half is real. What is *not* here: provisioning,
rotation, and revocation as a managed lifecycle. Keys are generated by a local CLI into `seed/identity/`;
"rotation" is re-running `mint`; there is no revocation surface at all, so a leaked token is valid until it
expires. The README calls this out under Scope boundaries; it is repeated here because the gap is
security-relevant, not cosmetic. Post-prototype fix: a real issuer with rotation and a revocation/status
list the gateway consults.

**4. `mcp-market-data` is two things under one name.** It is both the read-only perception server
(competitor prices, demand, inventory) *and* the embedded scenario driver that mutates market state on a
timeline (`packages/mcp-market-data/src/index.ts`, gated by `SCENARIO_TICK_SCALE` / `SCENARIO_LOOP`). That
is convenient for a one-command demo — the thing the agent perceives and the thing driving the narrative
are the same process — but it means there is no way to point the agent at a *real* feed without also
excising the driver. Post-prototype shape: perception behind an interface, with the scenario driver as one
adapter and a live feed as another.

**5. The gateway rate-limit is a coarse backstop, not the real limiter.** `infra/agentgateway/config.yaml`
sets a generous `localRateLimit` (120 tokens) on the MCP route, with a comment saying exactly why it is
generous: the *real* limits — per-tool counting, revenue-magnitude math, and a demand baseline for anomaly
detection — need state the gateway cannot compute, so they live in the control-plane circuit breakers. The
gateway number is deliberately loose so it never masks a breaker trip. If someone tightens the gateway
limit to "look safer," they can hide the very breaker behaviour the demo is meant to show. Leave it loose;
the breakers are the control.

**6. Sonnet 5 rejects the `temperature` parameter, so the recipe sets none.** Claude Sonnet 5 (and some
other newer models) return HTTP 400 on the OpenAI `temperature` param outright. The Goose recipe therefore
omits `temperature` entirely rather than pinning a value (`packages/agent/recipe.yaml`; documented in the
README Troubleshooting). This is load-bearing: adding a `temperature` back "for determinism" breaks the
default Bedrock path. If another model rejects a different param the same way, the fix is to *omit* that
param, not to change its value.

**7. Default LLM is a generic OpenAI-compatible endpoint, not Bedrock.** The committed gateway `llm:` block
routes to `LLM_BASE_URL`/`LLM_MODEL`/`LLM_API_KEY`; the Bedrock/Claude path is a commented block in
`infra/agentgateway/config.yaml` you switch on by hand. The prototype was verified live on Bedrock Sonnet 5,
but the *committed default* is the generic one so the demo runs against any OpenAI-compatible server without
AWS credentials. Which provider serves a request is decided entirely in the gateway; the agent stays
provider-agnostic. Accepted: a reader who wants the Bedrock path must edit the config, as the README's
[LLM provider configuration](../README.md#llm-provider-configuration) describes.

**8. Single agent, single domain.** One revenue-optimizer over one commerce domain. There is no
multi-agent composition, no negotiation, no cross-agent trust — those belong to Archetype 5
(`../../5-collaborating-self-directed-agents/`), not here. The policy, identity, and accountability
machinery is built to be per-agent, so composition is an addition rather than a rewrite, but it is an
addition that is not built.

## Deployment & tooling

**9. The container runtime is Finch (Lima), and host addressing reflects that.** The observability stack
runs under `finch compose`, which uses a Lima VM. The gateway runs on the **host**, not in a container, so
Prometheus scrapes it across the VM boundary at `host.lima.internal:15020` (`infra/prometheus/prometheus.yml`).
The compose file also maps `host.docker.internal:host-gateway` as an `extra_host` so a Docker-Desktop user
gets a working alias too, and the Grafana panel note spells out both. If you are on Docker Desktop and the
scrape target shows down, `host.docker.internal` is the alias to use. The gateway's metrics bind is
`0.0.0.0:15020` to make this cross-boundary scrape possible — on a shared machine, firewall that port or
revert to loopback.

**10. The gateway tolerates an absent OTel collector; traces are best-effort.** AgentGateway tries the OTLP
endpoint (`:4317`) and continues if nothing is listening, so the gateway and agent come up with or without
the `finch compose` stack. The consequence is that observability is *not* a hard dependency of the control
path: the policy gate, escalations, breakers, and kill switch all work with the collector down — you just
get empty Grafana panels. Accepted, and arguably correct for a demo, but worth stating: a missing trace is
silent, not an error.

**11. The dashboard is untyped and unauthenticated.** The operator dashboard (kill switch, breaker view,
Approve/Reject buttons) is served as static HTML/vanilla JS from the control plane
(`packages/control-plane/public/`), outside the TypeScript project — so the one surface that holds the
kill switch and the approval buttons is the only one with no type checking, no auth, and no production
styling. The README names it "a stage prop for the demo." The API it calls is the same path the
`approvals-cli.js` uses, so the buttons are not faking it; the surface around them is just unhardened.

## Testing

**12. Tests run compiled `dist/`, not the TypeScript directly.** `pnpm test` does `pnpm -r build` first,
then `node --test` over `packages/*/dist/**/*.test.js` plus the repo-level `scripts/**/*.test.mjs`
(the `.env.example` completeness check). Two consequences: every run pays a full rebuild, and a *stale*
compiled test could in principle contribute a phantom pass if the build step were ever skipped — which is
why the build is wired into the `test` script rather than left to the caller. Node's native type-stripping
would remove both the cost and the failure mode later. The suite covers the pure logic modules (tier
classification, escalation lifecycle, decision-trail hash chain + tamper detection, circuit breakers,
oversight state + dead-man's-switch, checkpoint store, commerce DB); it does **not** exercise the servers
end-to-end, the gateway CEL, or the Goose loop — those are demonstrated by running the demo, not asserted
by a test.

## Demo behaviour with a capable model

**13. The circuit breaker is a backstop, and the demo does not rely on it firing.** M5's rate/magnitude/
anomaly breakers (`packages/control-plane/src/breakers.ts`) are real and still sit in the `set_price` path
— a burst of deep cuts, a >$50k magnitude move, or an EXTREME demand z-score halts the agent. But the
demo's bad-data beat (a competitor feed fat-fingering a 75%-off across its whole catalog) does **not** trip
it, because a capable model (Claude Sonnet 5) *reasons* that a catalog-wide 75% cut is implausible and
declines to act — so no cascade of cuts is ever proposed. Rather than dumb the scenario down until the
model takes the bait, the agent has a `report_anomaly` tool (policy server) that records "I saw bad data
and stood down" to the decision trail, which the control plane surfaces on the dashboard. So the demonstrated
safety story is the model's *own judgment*, made visible and auditable; the breaker is the mechanical
backstop for a **weaker** model that fails to catch it. Both are real and both are wanted. Do not remove
the breaker because the demo does not exercise it, and do not weaken the glitch to force a breaker trip —
the point is that a good agent shouldn't need the breaker here, and a good system has it anyway.

## Invariants — do not "fix" these while working on something else

The following are load-bearing and must survive any future refactor of the above verbatim:

- **No path from reasoning to a commerce write skips the policy server.** The gateway owns identity and
  tool-scope; the policy server owns argument-level tier routing; `mcp-commerce` only ever sees writes the
  policy server forwarded. This is the whole point of the architecture (item 2).
- **The decision trail and checkpoint chain are append-only and hash-chained.** `verifyChain()` on either
  must stay meaningful — never rewrite history in place, and keep tamper detection pointing at the exact
  broken record. Retention pruning keeps the *chain* verifiable, not just the count.
- **The gateway rate-limit stays loose; the breakers are the real control** (item 5).
- **The circuit breaker stays in the write path even though the demo doesn't trip it** (item 13). The
  agent's `report_anomaly` judgment and the mechanical breaker are complementary layers — keep both.
- **The recipe omits `temperature`** (item 6) — do not reintroduce it.
- **Non-vacuous tests.** Every test that filters a collection down to violations must first assert the
  collection was non-empty, so an empty scan fails loudly instead of certifying nothing (enforced by the
  env-docs test's `found.length > 0` guard and mirrored across the suite).
